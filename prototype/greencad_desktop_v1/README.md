# GreenCAD Desktop 0.6 — автоматическая расстановка расчётных типов

Один подготовленный DXF → расчётные шаблоны и правила → предварительная
расстановка в выбранной зоне → проверка → ручное принятие → новый DXF.

**Быстрый опыт:** запустите `START_GENERATION_WINDOWS.bat`, затем «Расставить типы…».
В примере доступны четыре анонимных типа и 6 существующих ручных посадок. Выберите
T1–T4, лимит 20 новых экземпляров каждого, шаг 1 м и нажмите «Построить вариант».
Новые позиции сначала показаны пунктиром; «Применить вариант» записывает их одним
действием Undo. Ручные посадки не перемещаются и не удаляются.

**Правила общие с проверкой плана и картой**, а не считываются с изображения.
Генератор принудительно включает в частное задание зелёную зону, исключённые площади
и межпосадочное расстояние; эти флажки сохранятся в проекте только при применении.
Неизвестные обязательные данные — не разрешение. Все численные TEST-пороги остаются
тестовыми; это не нормативное заключение и не глобально оптимальная композиция.

Можно менять очередь типов, верхние лимиты и шаг. Есть отмена расчёта, отчёт причин,
экспорт JSON, сохранение/экспорт принятого результата. «Результат…» не является
полным ботаническим подбором: назначение конкретного растения проверяется отдельно.
Алгоритм последовательно заполняет область с одной стороны, не оптимизируя эстетику.

- [Как пользоваться и как работает алгоритм](docs/GENERATION.md)
- [Как обновить существующую папку 0.5](docs/UPGRADE_0_6.md)
- [Протокол проверок](test_results/GENERATION_TESTS.md)

Новых зависимостей и миграции .gcp относительно 0.5 нет. Исходные справочники не менялись.
Обычный `START_WINDOWS.bat` открывает прежнее демо с графическими типами — перед генерацией
им необходимо включить самостоятельные расчётные профили. Для первого опыта используйте
запуск GENERATION выше. Без окна — `tools/generate_layout.py`.

**Далее — документация возможностей предыдущих версий; их границы не описывают
весь текущий функционал 0.6.**

# GreenCAD Desktop 0.5 — расчётные шаблоны и подбор растений

Проектный тип теперь может иметь расчётный профиль **без выбранного вида**. Настройте
размеры/требования → проверьте тип или постройте карту → подберите реальные растения по
каталогу → при назначении повторно проверьте реальные требования. Неизвестное не считается
подходящим. Радиус знака не подменяет расчётный резерв.

**Быстрый пример:** `START_TEMPLATES_WINDOWS.bat` или открытие `examples/demo_templates.gcp`.
В нём четыре анонимных типа и шесть ручных посадок; все числа — тестовые условия проекта.

объяснения по всем 329 записям. Дополнительных видов и неизвестных размеров в базу не добавлено.

# GreenCAD Desktop 0.2

Локальный **ручной** двумерный редактор:

**один подготовленный DXF → интерактивная карта → ручные посадки → новый DXF.**

Есть импорт, карта, исходные слои, выбор проектного типа, добавление/перенос/удаление/копирование посадок,
редактирование координат, выбор растения из 329 исходных записей, настройка проектных типов,
отмена/повтор, сохранение переносимого проекта и проверяемый экспорт.

**Добавлена кнопка «Проверить допуски», выбор 13 реализованных проверок и отчёт по всем посадкам.**
Настройки сохраняются в проекте. Есть результаты PASS / FAIL / UNKNOWN / ERROR и отдельные
рекомендации. Перенос делает отчёт устаревшим. Подробности: [docs/VALIDATION.md](docs/VALIDATION.md).

**Это не полный нормативный профиль:** начальные численные отступы — явно тестовые проектные
параметры. Нет авторасстановки, физической модели загрязнений, полной повидовой оценки пригодности
и автоматического снятия ограничений при корнезащите. Черновые нарушения разрешено редактировать.

**Обновление существующей папки описано в [docs/UPGRADE_0_2.md](docs/UPGRADE_0_2.md).**
При обновлении с 0.1 повторно запустите `setup_windows.bat` для установки Shapely.
Старые `.gcp` читаются; новые записываются с версией схемы 2. После открытия нужна новая проверка.

## Быстрый запуск на Windows

1. Полностью распакуйте ZIP в отдельную доступную для записи папку, например `D:\GreenCADDesktop`.
   Не запускайте программу прямо из окна архиватора. Старый веб-проект не изменяйте.
2. Нужен **Python 3.12 или 3.13, 64-bit**, с компонентами **pip** и **Tcl/Tk**. Сборка проверена на
   Python 3.13.5 / Tk 8.6 в Linux. Код использует совместимый с Python 3.12 синтаксис;
   Windows и Python 3.12 в среде автора этой сборки не запускались.
3. Один раз запустите `setup_windows.bat`. Он создаёт `.venv` в этой папке и устанавливает зависимости.
   Интернет нужен для установки библиотек; сама программа работает локально без сетевых запросов.
4. Запустите `START_WINDOWS.bat`. По умолчанию откроется **пустой демонстрационный участок**.
   При следующих запусках достаточно этого файла.

То же через PowerShell, находясь в распакованной папке:

```powershell
py -3.12 -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r requirements.txt
.\.venv\Scripts\python.exe run_editor.py
```

Открыть конкретный файл:

```powershell
.\.venv\Scripts\python.exe run_editor.py "D:\My plans\input.dxf"
```

`setup_windows.bat` сначала пробует Python 3.12 и 3.13 через `py`, затем Python из PATH. Существующая виртуальная
среда старого GreenCAD не используется. Если установка не удалась, не закрывайте консоль: причина будет
видна в выводе pip. Если `tkinter` отсутствует, измените установку Python, включив Tcl/Tk.

## Первые пять минут

- Выберите **T1** слева. Включите **«+ Посадка»**. Щёлкните внутри участка несколько раз.
- Включите **«Выбор / перенос»** и перетащите один знак левой кнопкой мыши.
- Справа измените X/Y, метку, растение или проектный тип и нажмите **«Применить свойства»**.
  Выбор из каталога здесь НЕ означает проверенную пригодность растения.
- **«Настроить»** под списком типов меняет название, цвет, размер знака и растение по умолчанию.
  Для общей замены включите сброс индивидуальных назначений у всех посадок этого типа.
- **«Сохранить проект»** создаёт `.gcp`. **«Экспорт DXF»** создаёт отдельный новый `.dxf`
  и рядом отчёты `.export.json` и `.checks.json`. Затем откройте экспортированный DXF и продолжите двигать посадки:
  их ID и типы сохраняются.

Колесо мыши — масштаб под курсором; правая/средняя кнопка — сдвиг карты.
Фон можно двигать и левой кнопкой в режиме «Рука». `F` — вписать весь участок.
`Delete` — удалить выбранную посадку, `Ctrl+D` — копия со сдвигом (1 м, 1 м).
`Ctrl+Z`/`Ctrl+Y` — отмена/повтор (до 100 изменений). `Escape` отменяет незавершённое перетаскивание.
`Ctrl+S` — проект; `Ctrl+Shift+S` — проект под другим именем; `Ctrl+E` — экспорт DXF.
Привязка к сетке по умолчанию выключена. Сетка — вспомогательное изображение, НЕ сетка будущего алгоритма.

Двойной щелчок по исходному слою слева скрывает/показывает его; это НЕ удаление из экспорта.
Щелчок по газопроводу или другой исходной геометрии показывает её ID, слой, тип, роль и свойства.
Исходные объекты двигать нельзя. Исходные тексты скрыты по умолчанию; галочка «Подписи DXF» показывает их,
но содержание текстов никогда не используется для классификации.

`examples/demo_result.export.json` — результат повторного чтения и сравнения.
`python tools/make_examples.py` заново создаёт эти демонстрационные файлы.

## Какие форматы хранятся между экраном и DXF

Карта не является растровой фотографией. `Tk Canvas` рисует векторные примитивы по координатной модели.
В модели — метры, положительный Y вверх. Перевод в пиксели выполняет только `view.py`.
Перемещение вида и изменение масштаба не меняют координат проекта.

`.gcp` v3 — ZIP: **исходный DXF целиком**, `project.json` и `reference.json` (пакет справочников).
В манифесте есть версия схемы, SHA-256 основы, единицы, проектные типы, посадки, их свойства,
таблица соответствия слоёв, выбранные проверки, их параметры и параметры вида. Проект не зависит от первоначального расположения DXF.
Это не второй геометрический вход, а переносимая сохранённая сессия.

Экспорт начинается с повторного чтения сохранённых исходных байтов, а не с восстановления чертежа
по экранным полигонам. Удаляются только старые посадки с собственными корректными метаданными этой
программы; остальные элементы, в том числе в одноимённых слоях, не удаляются. Новые посадки получают
слои `GC_RESULT_<стабильный хеш ID типа>` и XDATA с ID, типом и свойствами.

Перед заменой выходного файла экспортёр читает временный DXF обратно, сравнивает исходные сущности
в modelspace/paperspace/блоках и исходные определения слоёв, проверяет количество и координаты новых
посадок. При несовпадении выходной файл не заменяется. Входной DXF нельзя выбрать целью экспорта;
также защищается его побайтово одинаковая копия.

**Это не побайтовое тождество DXF**: служебные заголовки, словари, таблицы и сериализация изменяются
при добавлении данных и записи через библиотеку. Область выполненного сравнения указана в отчёте.
Внешние CAD-приложения (AutoCAD, nanoCAD и др.) в этой среде не запускались.

## Как программа понимает, где трубы и бордюры

Используются только два явных способа:

1. **XDATA `GREENCAD_EDIT_V1` у объекта**: стабильный ID, `type_id`, `geometry_role`, свойства.
   Демонстрационный DXF размечен так и не требует соседнего файла.
2. **Точное сопоставление имени слоя**: `data/layer_mapping.json`, либо диалог «Соответствие слоёв».
   XDATA имеет приоритет. По части имени, цвету, надписи или форме условного значка семантика не угадывается.

Для произвольного файла неизвестные объекты отображаются как неклассифицированная подоснова.
Это не означает, что полный объектный контракт для них выполнен. Можно явно сопоставить слои и сохранить
профиль. В экспорте он помещается в наш XRECORD, не меняя свойства исходных сущностей.
Подробнее: **`docs/DXF_CONTRACT.md`**.

Каталог `data/plants_index.json` содержит 329 исходных записей из растительного реестра v1;
`data/site_types.json` — 140 идентификаторов из словаря территории v1. Они НЕ включают проверенные
размеры корней/кроны или готовый нормативный профиль; отдельный исполнитель описан в `docs/VALIDATION.md`. Пять начальных проектных типов — демонстрационные
графические шаблоны. Числовые радиусы шаблонов нельзя приписывать конкретным растениям из каталога.

## Границы версии

- Только DXF, не DWG и не произвольные архивы. Единый подготовленный файл со связанными данными внутри.
- Предпочтительный вход/выход — DXF **R2010**. Экспорт требует R2000 или новее.
- Просматривается **modelspace**. Листы и блоки сохраняются в исходнике; редактор не является средством
  подготовки печатных листов. Внешние ссылки не подгружаются и отмечаются как неполнота.
- Для плоской основы предусмотрены LINE, LWPOLYLINE/POLYLINE, CIRCLE, POINT; отображаются также
  ARC/ELLIPSE/SPLINE, обычные локальные INSERT и границы HATCH/MPOLYGON. Кривые упрощаются только
  для вида с параметром 0,025 м; их оригинальные данные не заменяются при экспорте.
- Штриховки с несколькими границами показываются **только контурами**: отверстия не закрашиваются.
  Рисунок штриховки, сложные шрифты, размеры, proxy-объекты, некоторые трансформации блоков и 3D
  могут отображаться неполно/схематично. Список замечаний доступен в «Состав DXF».
- Лимиты: 64 МиБ исходного DXF, 100 000 элементов modelspace, 600 000 вершин предпросмотра,
  20 000 ручных посадок. Это технические границы, а не обещание плавности на предельном объёме.
- Z показывается в проекции XY; исходные Z сохраняются. Новые посадки создаются в Z=0.
- Метры/миллиметры преобразуются явно. При `$INSUNITS=0` программа запрашивает масштаб;
  выбранное значение сохраняется в проекте и профиле экспорта, не переписывая исходный заголовок.
- Копирование результата в стороннем CAD с дублированием нашего ID будет отклонено при импорте.
  У новой посадки должен быть новый ID. Изменение центра знака в CAD учитывается по геометрии.
  Изменение радиуса символа в CAD не меняет общую спецификацию проектного типа: выдаётся замечание.
- Эта версия НЕ выполняет полное конкурсное ТЗ; здесь намеренно реализован только редактор и обмен.

## Запуск Linux и проверки

Нужны Python 3.12/3.13, Tcl/Tk и графическая сессия. На Ubuntu типичные системные пакеты —
`python3-venv`, `python3-tk`. Команды:

```bash
python3 -m venv .venv
.venv/bin/python -m pip install -r requirements.txt
./run_linux.sh
```

Проверка чтения без окна:

```bash
python run_editor.py --inspect examples/demo_block.dxf
```

Проверки стандартным `unittest`, без pytest:

```bash
python -m unittest discover -s tests -v
python tools/verify_export.py examples/demo_block.dxf examples/demo_result.dxf
```

На Linux без дисплея GUI-тесты пропускаются. Для их фактического выполнения нужен Xvfb:

```bash
xvfb-run -a python -m unittest discover -s tests -v
```

В Windows можно запустить `RUN_TESTS_WINDOWS.bat`. Тесты интерфейса ненадолго открывают обычные окна.
Фактические результаты и ограничения проверки: **`test_results/TEST_REPORT.md`**.
GUI не упакован как исполняемый `.exe` или Docker-приложение; внутри архива — исходники и скрипты запуска.

## Структура кода и продолжение

- `models.py` — данные, единицы и структурная валидация.
- `metadata.py`, `dxf_io.py` — DXF/XDATA, извлечение вида и независимый экспорт.
- `session.py` — команды редактирования, состояния, история.
- `project_io.py` — переносимое сохранение и контроль схемы.
- `catalog.py` — доступ к единому пакету справочников; `reference_build.py` — сборка; `reference_ui.py` — просмотр.
- `view.py` — преобразование координат и Canvas; не содержит DXF-операций.
- `ui.py` — панели, действия пользователя, диспетчер фонового чтения/экспорта.

Конкретный GUI можно заменить без изменения хранения координат и DXF-экспортёра. Правила из `checks.py`
получают снимок модели и возвращают отчёт; будущий генератор сможет формировать тот же список Placement.
Реализовано 13 выбранных проверок, не весь нормативный реестр. Версия схемы сохранения проверяется явно: неизвестная
версия отклоняется без изменения файла. Гарантировать отсутствие любых будущих миграций нельзя.

Подробности: `docs/ARCHITECTURE.md`, `docs/DXF_CONTRACT.md`, `docs/SOURCES.md`.
