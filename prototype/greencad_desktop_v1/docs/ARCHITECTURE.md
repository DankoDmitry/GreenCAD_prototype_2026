# Архитектура первого исполняемого редактора

Это модульное настольное приложение, не сеть микросервисов. Окно, команды и файловые адаптеры
разделены по обязанностям, чтобы будущая логика расчётов не зависела от Tkinter или координат пикселей.

## Поток данных

1. `dxf_io.load_dxf` читает **снимок байтов** одного DXF. Возвращает `Drawing` с неизменяемой основой,
   масштабом, объектами предпросмотра, замечаниями и импортированными ручными посадками.
2. `EditorSession` хранит проектные типы, посадки и историю. Команды add/move/change/delete/set_type
   не вызывают GUI, DXF и нормативные правила.
3. `MapCanvas` преобразует XY-метры в пиксели. Во время drag меняется только предварительное изображение;
   отпускание мыши вызывает одну команду move. Escape не меняет модель. Pan/zoom не меняют модель.
4. `project_io` сохраняет `.gcp` как архив из source.dxf + JSON. Проверяет версию и SHA256 при чтении.
5. `dxf_io.export_dxf` получает модель, заново читает основу, добавляет результат, повторно проверяет
   сохранность и только затем заменяет выбранный выходной файл.

Фоновый исполнитель занимается чтением DXF и экспортом; все обращения к Tk выполняются в главном
потоке. На время фоновой операции ввод команд блокируется, текущий рисунок остаётся видимым.
Управление циклическим GC на границе фоновой задачи предотвращает уничтожение Tk-переменных
закрытых диалогов на рабочем потоке. После завершения GC восстанавливается на главном потоке.

## Данные вместо общих внутренних объектов

- `ProjectType`: ID, название, графические параметры, растение по умолчанию, расширяемые свойства.
- `Placement`: ID, type_id, XY, необязательный собственный plant_id, флаги, метка, свойства.
- `Feature`: CAD-представление основы, handle, точный слой, тип, роль геометрии, источник классификации.
- `Primitive`: только упрощённый вид; никогда не используется для восстановления исходного DXF.

Конкретный формат таблиц находится за `catalog.py`. В сборку включены производные индексы, сохранившие
все исходные ID и контрольные суммы предыдущих реестров. Это не новый ботанический справочник.

## Исторические границы 0.1 (обновлены в 0.2)

Правила, вычислительные поля, оптимизация, проверка принадлежности зоны, экологическая пригодность,
распределение ресурсов и 3D. Свободное перемещение с неизвестной допустимостью — ожидаемое поведение.
Даже визуально зелёная область не является результатом нашего расчёта допустимости.

Будущее подключение правил может использовать список Placement, поля и снимок свойств территории,
вернуть отчёт, а интерфейс только отобразит его. Генератор может сформировать тот же список Placement.
Функции для таких подключений ещё не объявлены стабильным внешним API и не имитируются заглушками
«всегда разрешено». Формат сохранения имеет явную версию; изменение обязательной структуры требует
новой версии и мигратора. Расширяемый properties предназначен для дополнительных значений.

## Независимые проверки

Unit-тесты: импорт, масштабы, неизвестные величины, типизация, сохранение, история, экспорт.
GUI-тесты: реальные Tk-виджеты и события мыши, координаты после pan/zoom/drag, слой, свойства, диалоги,
сохранение и экспорт через UI. Успешные логи находятся в test_results.

Сохранность проверяется независимо от Canvas и списка команд. Пространственные/нормативные проверки
не подменяются этой файловой проверкой.

## Дополнение 0.2

Реализованы `check_geometry`, `checks`, `checks_ui` и описанный в `docs/VALIDATION.md`
проверяющий конвейер. Строки выше о неготовых проверках описывают исходную версию 0.1.
EditorSession хранит версионированные настройки; результат — производный снимок с fingerprint.
GUI вызывает тот же `validate_plan`, что headless CLI. Экспортёр DXF не принимает решений о допусках: рядом
с его проверкой сохранности записывается отдельный файл .checks.json с CURRENT/STALE/NOT_CHECKED.
Код не генерирует посадки, не исправляет нарушения и не активирует нормативные кандидаты автоматически.


## Версия 0.5: расчётный профиль не является ботаническим фактом

`ProjectType.template` содержит проектные требования и критерии кандидатов. `templates.py`
проверяет профиль относительно pinned ReferenceBundle, но не меняет сам пакет.
`match_catalog` выполняет типизированное сопоставление с источниками; `PointEvaluator`
проверяет либо профиль без вида, либо реальное растение вместе с явными условиями профиля.
`templates_ui.py` — отдельные диалоги ввода/просмотра, формул расстояний в них нет.
`calculation_target` и происхождение значений включены в отчёт. Карта получает явный флаг
`template_only`; он не влияет на полную проверку плана. После подстановки вида выполняется
повторная проверка, а не предположение о всеобщей взаимозаменяемости.

Дополнительные защитные условия `template.root_mode` и `template.catalog_match` — кодовые
инварианты нового типа, не новые нормативные строки. Их определения включаются в отчёт
вместе с профилями и списком фактически выполненных условий. `.gcp` v4 и DXF-профиль v2
не дают прежнему редактору молча проигнорировать новый расчётный смысл.


## 0.6 — генератор шаблонов

`GenerationOptions` фиксирует одну зону, очередь типов, новые квоты и шаг.
`generate_plan(make_request(session), options)` работает на частном снимке.
Общие `PointEvaluator` и геометрический адаптер не зависят от Tk. Принятие одной
кандидатуры обновляет частный индекс; отдельный полный проход `validate_plan`
пересоздаёт контекст после генерации. Подтверждение через `apply_generation`
сверяет хеш исходного проекта и целостность отчёта, затем создаёт одно действие Undo.

`generation_ui.py` только формирует задание, рисует неподвижный пунктирный preview
и вызывает применение. Общий executor не запускает два изменения плана одновременно.
Выборка сетки не читает `AdmissibilityMap`, а напрямую использует тот же исполнитель.
Настоящий список Placement изменяется только при применении; экспорт не читает Canvas.

Полные алгоритм, ограничения и схема данных: `GENERATION.md`.
