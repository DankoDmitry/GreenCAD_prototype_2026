# GreenCAD Desktop 0.5 — расчётные типы и подбор растений

## Назначение

Проектный тип теперь может иметь самостоятельный **расчётный шаблон** и оставаться без
назначенного растения. Профиль — условия проекта, не новая строка ботанического справочника.
Один класс `ProjectType` описывает множество редактируемых типов; экземпляры `Placement`
хранят координаты и `type_id`. Автоматического поиска позиций в этой версии нет.

Старые типы открываются без шаблона и продолжают работать прежним способом. Чтобы включить
новый режим, выберите тип слева → **«Настроить…»** → **«Расчётный профиль»** →
**«Использовать самостоятельный расчётный шаблон»**. Новый тип уже имеет пустой профиль.

## Быстрый опыт

Запустите `START_TEMPLATES_WINDOWS.bat` либо откройте `examples/demo_templates.gcp` через
«Открыть». В Linux: `python run_editor.py examples/demo_templates.gcp`.

Это прежняя небольшая подоснова с дорогами и осью газа, четыре анонимных расчётных типа
и шесть заранее выбранных вручную точек. Никаких фактических видов этим типам не назначено.
Размеры, минимумы, состояния грунта и A1 — **явные синтетические условия**, не ГОСТ/СП.

1. Выберите T1 → «Настроить…». Просмотрите профиль. Радиус кроны/резерв 1,5 м;
   режим корнезащиты FORBIDDEN; требование рыхлого и дренированного грунта.
2. «Проверить допуски»: все шесть точек демонстрационного проекта проходят выбранные
   условия именно как шаблоны, без видовых характеристик.
3. Перенесите одну точку к оси газа y=30 или к границе зелёной зоны. Повторная проверка
   обнаружит нарушение. Обычный масштаб карты на результат не влияет.
4. «Карта допустимости…» → T1 → «Проверять только расчётный шаблон…» → построить.
   Карта учитывает профиль T1, но не расстояния между уже расставленными посадками.
5. В карточке типа нажмите «Подобрать растения…». Есть поиск, фильтр результатов,
   подробности каждого критерия и источник фактического значения.

**В настоящем каталоге нет подтверждённых численных размеров кроны для этого подбора.**
Поэтому при включённой верхней границе размера у всех кандидатов категории будет UNKNOWN.
Это намеренный результат. Для опыта с реально имеющимся требованием можно в КОПИИ T1
очистить габариты и оставить «Требуется дренированный грунт». У тсуги канадской это требование
известно (V02205, источник и ячейка показаны), но отсутствующие размеры при этом не становятся
известными. В текущем каталоге также нет отдельной категории цветов/травянистых: выбор
`herbaceous` допустим для проекта, но не создаёт несуществующих растений в базе.

## Карточка проектного типа

### Название и знак

Категории: `tree` — деревья, `shrub` — кустарники, `herbaceous` — цветы/травянистые,
`vine` — лианы, `generic` — без ограничения категории. Эти категории служат проектной
классификации. Исходные строки сортов/групп каталога не объединяются.

Название, цвет и **радиус условного знака** — оформление. Этот радиус не участвует в
проверках. Можно назначить растение по умолчанию всему типу, оставить тип пустым или задать
индивидуальное растение отдельной посадке. Индивидуальное значение имеет приоритет;
явный флажок в карточке позволяет сбросить все такие назначения при массовой замене.

Есть «Копия типа» и «Удалить тип». Используемый посадками тип и последний тип удалить
нельзя. Изменения записываются одним действием в Undo. Копия получает новый ID, не новый
Python-класс. Ограничения объёма данных и интерфейса сохраняются: это не обещание
неограниченной памяти при любом числе типов.

### Расчётный профиль

| Свойство | Применение в версии 0.5 |
|---|---|
| Радиус кроны / резерв в плане | Условный круг проектного типа. Проверяется вместимость внутри области, отсутствие захода в исключённые площади и сумма радиусов при проверке соседних посадок. В подборе — верхняя граница диаметра кроны, равная 2R |
| Максимальный радиус корней | Только критерий подбора по `project.root_radius`; не подменяет радиус кроны и не создаёт новых правил вокруг коммуникаций |
| Максимальная полная высота | Только критерий подбора по `project.total_height`; пространственная модель остаётся XY |
| Описание расчётного состояния | Пояснение автора проекта. Числовые значения должны быть для сопоставимого состояния; программа не выводит возраст/сорт из названия |
| Пять требований к грунту/воде | «Не задано», «Требуется», «Не требуется». При активной почвенной проверке берутся как условия шаблона |
| Корнезащита | ANY — может использоваться; FORBIDDEN — не использовать; REQUIRED — обязательна. Это режим проекта, НЕ подтверждение применимости технологии к виду |
| Диапазон A1 | Две границы сценарной шкалы 0–1. Сопоставляется с A1 участка; не приравнивается к биологической влажности |
| Минимумы типа | Дополнительные проектные пороги для подключённых правил расстояния. Эффективен максимум общего и типового минимума; шаблон не ослабляет общее условие |

Профиль сам не включает выключенные правила. Вкладка **«Что нужно проверкам»** показывает
входы активных условий и отсутствующие сведения. Это проверка готовности ПРОФИЛЯ, не
готовности всей исходной геометрии/участка. Окончательный ответ даёт обычный исполнитель.

**Геометрическая модель резервирования — наше проектное решение, не биологическая норма.**
При радиусе R центр должен находиться внутри зелёной зоны, а расстояние до границы
объединения зон, включая отверстия, — не менее R. До исключённых площадей нужно не менее R,
при центре снаружи; касание разрешено. Положительные радиусы задают проектный запрет на
перекрытие резервов даже там, где реальная крона могла бы нависать над покрытием.

При проверке межпосадочного расстояния используется:

`required(i,j) = max(общий минимум, минимум типа i, минимум типа j, R_i + R_j)`.

Незаполненный резерв означает отсутствие дополнительного ограничения этой модели, а не
доказанную нулевую крону. В остальных проверках расстояния измеряются по прежнему основанию
(например, от центра до AXIS газа). Корнезащита никаких порогов автоматически не уменьшает.

### Дополнительные критерии подбора

Можно добавлять, редактировать и убирать условия по зарегистрированным характеристикам
растения/проектного состояния: равенство, верхняя/нижняя граница, попадание в диапазон,
выбор из списка, включение значений множества, покрытие диапазона. Единицы берутся из
описания параметра, свободные формулы не исполняются. Для числовых диапазонов и списков
в диалоге разделитель `;`, например `1; 3`. Для булевых значений — `Да` / `Нет`.

Условие по интервальному значению требует включения всего исходного интервала в заданный;
одно пересечение не доказывает соответствие (частичное перекрытие → UNKNOWN). Операция
«Допускает весь диапазон» требует, чтобы интервал из каталога покрывал нужный интервал.
Контекст территориальной отметки задаётся явно. Фильтр `PLUS` по рекомендациям — сознательное
условие автора шаблона, не превращение рекомендации ГОСТом в обязательный запрет.

Произвольный новый параметр/операция требует регистрации в реестре и адаптере, а не ввода
названия наугад. Поддерживаются до 40 дополнительных критериев; метаданные профиля
ограничены 8 000 ASCII-символами JSON для безопасной переносимости в DXF.

## Подбор и подстановка — разные операции

Незаполненный необязательный критерий шаблона не участвует в подборе. Но отсутствие
значения растения по ЗАДАННОМУ критерию — **UNKNOWN**, не автоматический успех.

- **Соответствует критериям**: выполнены все заданные фильтры с имеющимися данными.
- **Не соответствует**: есть конкретное несоответствие; назначение из списка блокируется.
- **Недостаточно данных**: назначение разрешено только после подтверждения, как черновик.
  Исполнитель сохраняет UNKNOWN, а не скрывает отсутствие сведений.

При наличии и нарушений, и пропусков общий результат FAIL, но подробности сохраняют всё.
Результат PASS подбора НЕ означает, что растение подходит ко всем посадочным местам.
Режим корнезащиты и условный A1 не проверяют ботаническую пригодность технологии или
устойчивость к реальному загрязнению; эти ограничения явно показаны рядом с результатом.

Почвенные требования при подборе сравниваются по силе, а не по простому равенству:
растение с явно отсутствующим требованием может занять более требовательный шаблон;
растение с требованием не должно занимать шаблон, объявивший его ненужным. Отсутствие
исходной записи не трактуется как `false`.

## Общие проверки для типов и растений

`PointEvaluator` использует прежние операторы и один `ReferenceBundle`.

- Нет вида, есть шаблон: берутся его расчётные требования. Незаданный обязательный вход
  даёт UNKNOWN. Источник обозначается PROJECT_TYPE, а не ботаническим документом.
- Назначен вид: выполняются реальные требования из справочника **и** явные требования
  профиля. Более мягкий шаблон не отменяет более строгое требование растения. Вид может
  дополнить неуказанное требование типа; шаблон не заполняет неизвестное значение вида.
- Подстановка дополнительно проверяется на соответствие типу (`template.catalog_match`).
- Режим корнезащиты сравнивается с флагом отдельной посадки (`template.root_mode`).
  Новая посадка типа REQUIRED создаётся с включённым флагом; уже существующие экземпляры
  автоматически не изменяются и могут показать нарушение.

Два дополнительных защитных условия подключаются при проверке типа автоматически, когда
есть выбранные проверки и они применимы. Они видны в подробном отчёте и компонентах карты.
Пустой список выбранных правил остаётся NOT_CHECKED; выбор только PLAN-проверок не даёт
зелёную статическую карту за счёт одних дополнительных условий.

После назначения растения через карточку типа или изменения индивидуального вида в
панели свойств запускается повторная проверка существующих посадок (если они есть).
Она не перемещает объекты и не откатывает черновые назначения. При изменении остальных
данных старый отчёт помечается как устаревший, обычная кнопка проверки остаётся доступной.

Карта по умолчанию учитывает назначенный вид. Флажок **«Проверять только расчётный шаблон»**
позволяет явно игнорировать даже назначенный вид для предварительного исследования;
это подписано на карте. Полная проверка плана всегда использует фактические назначения.
Смена профиля обесценивает прежнюю карту/отчёт. Цвет сетки относится только к центру клетки.

## Сохранение, DXF и совместимость

Проекты `.gcp` теперь имеют схему **4**; схемы 1, 2, 3 читаются с прежними правилами
миграции справочников. Шаблоны хранятся в `state.types[].template`, значения сценария —
отдельно, `reference.json` остаётся неизменяемым снимком базы. После открытия нужна новая
проверка. Редактор 0.4 отвергает схему 4: перед пересохранением оставьте копию старого файла.

В исходных DXF сущностях по-прежнему ничего не переписывается. В экспортируемых метаданных
новых посадок/типов сохраняется профиль. У файлов с шаблонами версия нашего XDATA/XRECORD — 2.
Эту версию читает 0.5; 0.4 отвергает её, чтобы не потерять новый смысл молча. Сам DXF
остаётся обычным CAD-файлом с символами; вне GreenCAD сторонний CAD не выполняет проверки.
Взаимодействие с внешним CAD здесь не испытывалось. Повторный экспорт проверяет сохранность
исходных сущностей, координат и полного набора проектных типов после чтения результата.

Исходные XLSX/JSON и скомпилированный `reference_bundle.json.gz` в этой доработке не
изменялись. `python tools/build_reference.py --check` подтверждает воспроизводимость пакета.
Новых нормативов, растений и выдуманных размеров в базу не добавлено.

## Модули и воспроизводимые команды

- `templates.py`: контракт профиля, типизированный фильтр каталога, зависимости проверок.
- `templates_ui.py`: редактор типа/критериев, список кандидатов, источники, подтверждение черновика.
- `models.py`: необязательное поле `ProjectType.template`.
- `checks.py`: общий контекст шаблона/вида, резервы, минимумы, дополнительные защитные условия.
- `admissibility*.py`: тот же вычислитель с явно заданным режимом template_only.
- `project_io.py`, `metadata.py`, `dxf_io.py`: версии и безопасная передача профилей.

```text
python tools/build_reference.py --check
python tools/check_plan.py examples/demo_templates.gcp --output checks_templates.json
python tools/match_plants.py examples/demo_templates.gcp --type T1 --output candidates.json
python tools/map_admissibility.py examples/demo_templates.gcp --type T1 --template-only --step 2 --output template_map.json
```

Коды CLI подбора: 0 — корректно построен список (включая пустой список соответствующих),
2 — ошибка входа/сохранения. CLI не меняет проект. Пример воссоздаётся отдельным
`python tools/make_template_example.py`, содержащим шесть ручных координат, не генератор.

## Границы

Нет авторасстановки, новой нормативной сверки, автоматического конструирования безопасного
набора взаимозаменяемых видов, моделирования роста, корневой геометрии или физических полей
загрязнения. Программа не выводит размеры по названию или фотографии растения. Сценарии
A1/грунта по-прежнему постоянны на участке. Объектные ограничения зависят от выбранных
активных правил; отсутствие иных подключённых критериев не означает комплексного допуска.

Проверка нативной Windows и AutoCAD/nanoCAD не выполнена. Проверены Linux/Tk/Xvfb,
сохранение/обратное чтение, реальные GUI-события и происхождение данных. Протокол —
`test_results/CALCULATION_TEMPLATES_TESTS.md`.
