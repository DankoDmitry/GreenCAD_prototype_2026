# Контракт ограниченного редактора — версия 1

Это **проектное** соглашение GreenCAD, не утверждение о том, что ГОСТ предписывает наши имена слоёв.
Объекты и названия связаны с ранее подготовленными реестрами через стабильные `type_id`.

## 1. Вход и координаты

Один DXF, предпочтительно R2010, основная геометрия в modelspace. Произвольные DWG-пакеты, сборка
XREF и восстановление смысла легенд находятся вне этого адаптера. Внешние ссылки не разрешаются.

Внутренние координаты — мировые X/Y в **метрах**. Основа координат DXF сохраняется, включая большие
геодезические смещения; перевод вида в пиксели выполняется отдельно. `$INSUNITS` нужен для масштаба.
Для Unitless обязательна явная положительная величина «метров в единице DXF». Например, 0.001 для мм.
Исходные Z не переписываются; только изображение проецируется в XY. Новые знаки имеют Z=0.

## 2. Метаданные элемента

В XDATA приложения `GREENCAD_EDIT_V1` хранится JSON, разбитый на ASCII-строки длиной <=200 байт,
каждая строка с групповым кодом 1000. Unicode экранируется `ensure_ascii=True`; порядок фрагментов
сохраняется. Общий размер нашей записи ограничен 12 000 байт. APPID регистрируется в DXF.

```json
{
  "schema_version": 1,
  "role": "asset",
  "id": "gas_01",
  "type_id": "net.gas",
  "geometry_role": "AXIS",
  "properties": {
    "synthetic": true,
    "depth_m": null,
    "pressure_category": null,
    "A01": null
  }
}
```

`id` однозначен в файле. `type_id` ссылается на объектный словарь; незнакомый строковый ID сохраняется,
но не означает автоматически поддержанную вычислительную семантику. `properties` — расширяемые
данные, а НЕ исполняемые выражения. Незаданный параметр хранится как `null`, не как ноль.

Роли, используемые профилем: `AXIS`, `EDGE`, `CENTER`, `BOUNDARY`, `AREA`, `OUTER_CONTOUR`, `SYMBOL`,
`CONTEXT`. Ось трубы не становится её внешней поверхностью; условный знак не определяет физический габарит.

В этой версии `Feature` представляет CAD-элемент и его вид. Это не полный граф физических объектов
территории. Отношения «несколько сетей — общая трасса» могут храниться в `properties`, но отдельного
вычислительного обработчика таких отношений пока нет. Ни одна функция допустимости не делает
предположения «одна линия — одна физическая сеть», потому что таких функций здесь ещё нет.

## 3. Сопоставление по точному имени слоя

Альтернатива для геометрии без XDATA:

```json
{
  "schema_version": 1,
  "layers": {
    "GC_GAS_AXIS": {"type_id": "net.gas", "geometry_role": "AXIS"},
    "GC_CURB_EDGE": {"type_id": "traffic.curb", "geometry_role": "EDGE"},
    "GC_GREEN_ZONE": {"type_id": "context.green_zone", "geometry_role": "AREA"}
  }
}
```

XDATA имеет приоритет. Без обоих способов объект остаётся `UNCLASSIFIED`.
`TEXT`, `MTEXT`, `ATTRIB`, `DIMENSION` и другие явно аннотационные верхнеуровневые объекты не
становятся сетями по текстовому содержимому даже на сопоставленном слое. Локальный INSERT
рассматривается как контейнер геометрии; содержимое надписей внутри не используется как классификатор.
Программа не удаляет ни аннотации, ни неизвестные сущности из исходного документа.

Сопоставление сохраняется в `.gcp` и в XRECORD `GREENCAD_EDITOR_PROFILE_V1` выходного DXF.
XRECORD содержит schema_version=1, metres_per_unit, layer_mapping и project_types. JSON разбивается
на строки с кодом 1. Это собственный профиль приложения, не изменение смысла исходных CAD-слоёв.

## 4. Выходные посадки

Одна посадка — один `CIRCLE` (графический круг с известным центром) либо `POINT`. Результат получает
слой `GC_RESULT_<первые 10 hex SHA256(type_id)>`. Существующий одноимённый слой не перекрашивается.
Цвет задаётся самой новой сущности (`true_color`). Для POINT внешний CAD может использовать собственный
`PDMODE`, поэтому внешний вид точки в других программах не обязан совпадать с нашим ромбом.

```json
{
  "schema_version": 1,
  "role": "placement",
  "placement": {
    "id": "stable-unique-id",
    "type_id": "T1",
    "x": 18.0,
    "y": 16.0,
    "plant_id": null,
    "root_protection": false,
    "locked": false,
    "label": "P1",
    "properties": {}
  },
  "project_type": {
    "id": "T1", "name": "Крупное дерево", "category": "tree",
    "radius_m": 3.0, "color": "#2C7553", "plant_id": null,
    "symbol": "circle", "properties": {}
  },
  "geometry_role": "SYMBOL_CENTER",
  "validation": "NOT_IMPLEMENTED"
}
```

`plant_id=null` у посадки означает наследование назначения из проектного типа. Если там тоже null,
конкретное растение не выбрано. После изменения в стороннем CAD положение читается из геометрии,
а не из дублированных координат XDATA. Радиус относится к общему типу, поэтому при расхождении с
внешне изменённым кругом выдаётся замечание. Смена вида/типа, координат и свойств в редакторе сохраняется.

Повторный импорт распознаёт только наш namespace и версию. Дубли ID, конфликтующие определения типа,
неподдерживаемые версии или повреждённый JSON дают ошибку, а не молчаливое удаление данных.
Удаление всех старых элементов только по префиксу слоя запрещено: экспорт удаляет лишь распознанные
собственные посадки из снимка, затем добавляет актуальный список. Это предотвращает дублирование.

## 5. Проверка сохранности

Файл назначения создаётся атомарно через временный файл в том же каталоге. До замены выполняется
повторное чтение. Сравниваются DXF-теги исходных графических сущностей во всех блоках и пространствах,
а также ранее существовавшие определения слоёв. Самостоятельно добавляемые записи и распознанные
старые посадки не входят в набор неизменяемых сущностей. Также проверяются ID, число и координаты
актуальных посадок. Абсолютный допуск сравнения координат — 1e-8 м.

Это проверка структурного сохранения в пределах API `ezdxf`, не доказательство одинаковой отрисовки
во всех CAD и не побайтовое сравнение файла. Заголовки, APPID, собственный XRECORD и служебные данные
могут изменяться при сериализации. Проверки нормативной допустимости не выполняются.
